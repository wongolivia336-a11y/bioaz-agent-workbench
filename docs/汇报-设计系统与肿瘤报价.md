# 汇报讲稿 · 从工程实现到设计语言：肿瘤报价的转译

> 约 12 分钟。方括号里是操作提示，不用念。
> 演示：`?line=dmpk` / `?line=tumor` 两个窗口并排。

---

## 开场（40 秒）

各位老师好。

今天想汇报的不是"我做了哪些页面"，而是**一个转译的过程**：
工程师已经把肿瘤报价的功能实现出来了，功能是齐的；
但它是**工程思维的产物**——而我们这套工作台已经有自己的设计语言了。

我的工作是把前者翻译成后者。**这中间的判断，才是我想讲的东西。**

我分四段：**我怎么诊断那一版、转译依据的三条原则、肿瘤报价和 DMPK 到底
同什么不同什么、以及这些判断怎么沉淀成设计系统。**

---

## 一、诊断：工程实现和设计语言，差的不是审美（3 分钟）

### 1. 三个症状

我第一次看那一版，记下了三件事：

- **一张很长的下拉框表单**，十五个字段一次铺完
- **空表单上先挂着五条红字**，写着"缺少必选参数"
- **右栏台账每一行都标着"未提交"**，同时输入框那边也标了一次

### 2. 每一个背后都是一个立场，不是一个样式

这一步我想讲慢一点，因为**如果只当成"不好看"去改，改完还会长回来**。

**第一个，长表单。**
它背后的假设是：**任务是"把表填完整"**。所以字段有多少就摆多少，一次问清。
这个假设在数据录入系统里是对的。

但我们这套东西的假设不是这个。中间是一条对话流——
**任务是"把这件事往前推一步"**。人说一句话，数字同事认出能认的，
再问缺的。表单在这里不是主角，**它是对话的一个回合**。

所以不是"表单太长了要收起来"，是**表单的位置从"主界面"变成了"一次回合"**。
这两种说法会导出完全不同的改法。

**第二个，空表单上的红字。**
它背后的假设是：**没填 = 不合法**。技术上讲得通——校验器跑一遍，
必填项为空，返回错误。

但从人的角度：**没填不等于填错。** 一张还没动过的表单上先挂五条错误，
是在为**尚未发生的错误**问责。人第一眼看到的是"我做错了五件事"，
而他还什么都没做。

改法是把这句话拆开：
- **缺多少** → 写在卡头上，"还需填写 3 项"，中性陈述
- **依赖没满足** → 给中性灰占位，"请先选择模型"，不是错误是顺序
- **红字** → 留给真正的冲突

[演示：肿瘤报价空表单，卡头计数]

**第三个，两处都标"未提交"。**
这个最典型。工程实现的直觉是：**状态是数据，凡是能显示的地方都显示**。

但对使用的人来说，**同一个状态在两个地方各标一次，他得先判断哪个是真的**。
"选了还没发"这件事天然属于输入框——它就在手指旁边。
右栏台账应该只显示已经落库的值。

**一件事只在一个地方说。** 这是我后面反复用到的一条。

## 二、转译的三条原则（3 分钟）

### 原则一：统一落在骨架上，不落在控件上

这一条我想举一个具体例子，因为它是最容易做错的地方——
**"统一"很容易被做成"长得一模一样"。**

肿瘤报价的模型选项是中英双语的，八项，最长一条 437 像素。
我试过把它们平铺成选项按钮，跟 DMPK 一样：
**渲染出来 127 像素高、折 4 行**，而 DMPK 那边一行只有 28 像素。

[演示：两边并排，DMPK 的选项按钮 vs 肿瘤的下拉]

所以长选项必须走下拉。**这不是妥协，是同一套规范下的另一个正确取值。**

那"统一"落在哪儿？落在**行的骨架**上——
序号圆点、标签、必填标记的位置、间距、选中态的表达方式。
这些一致了，两条线就是一个东西；控件类型不一样，反而是尊重了内容。

**一致性不是长得一样，是同一套判断在不同内容上给出各自正确的答案。**

### 原则二：视觉权重要映射可交互性

[演示：右栏切到「报价规则」]

这一栏我分了上下两段，形式**故意不一样**：

- **上半段「本次命中的规则」**——有卡片、有边框、有按钮。因为它可改。
- **下半段「全局规则」**——素文本行，只有一个跳转箭头。因为它在这儿只能看。

**能改的有实体，只能看的退成文本。** 这样"哪些我能动"不需要读文字就知道。

如果两段长一样，就必须靠一句说明去解释——而人不读说明。

### 原则三：一件事只在一个地方说

前面"未提交"那个是这条。还有一个更大的应用，我放在下一段讲。

## 三、肿瘤报价和 DMPK：同什么，不同什么（4 分钟）——重点

### 1. 相同的部分

**节奏相同**：一句话识别 → 逐项补全 → 报价前确认 → 生成产物 → 回头改参数。
这条链路是 DMPK 走通的，肿瘤报价照这条走。

**骨架相同**：参数卡、字段行、已选参数托盘、右栏台账，是同一套。

**入口位置相同**：想改某一项，去右栏点那一行的铅笔；
想整体看，展开参数卡；想一屏看全，进全屏。**手的位置不用重新学。**

**说法相同**：右栏那一栏两边都叫「参数收集」，齐全之后都变成
「报价参数 · 已确认」。**同一件事在两条线上叫两个名字，人会以为是两个东西。**

我逐项核对过参数卡：宽度 848、圆角 8、内距 12/14、行距 18、四组分页——
**两边完全一致。** 一致性我不靠"看着差不多"，我是量出来对照的。

### 2. 不同的部分，而且是有意不同

**词表和分组不同。** DMPK 分「检测类型 / 动物实验 / 生物分析 / 报告与报价」，
肿瘤分「模型与动物 / 实验设计 / 给药方案 / 检测与交付」。
业务不一样，分组就该不一样。

**控件类型不同。** 上面讲过。肿瘤这边多了三种：长选项走下拉、
检测指标是多选、分组给药剂量是**可重复的行**——一行就是一个实验组。

[演示：分组及给药剂量，添加一行]

这一项我加了一句填写说明：「请明确填写对照组，对照组剂量可以为 0 或非零」。
这句话是必要的——**对照组剂量填 0 还是填别的，决定了报价里算不算
这一组的给药操作费。人不问就会漏。**

**互斥关系不同。** 检测指标里有一项「不需要检测」，
它和「IVIS 成像」同时选中是一句自相矛盾的话。
我把它做成互斥，而且**两个方向都清**——先勾 IVIS 再勾"不需要"，
和反过来，结果必须一样。只做一个方向的话，两条路会给出不同结果，
**而人不会知道这两条路不一样。**

**少了三个面板，也是有意的。** DMPK 有「退回批注 / 审核记录 / 交接工单」，
那几样是它走通整条送审链路之后长出来的。肿瘤报价现在还没有那条链路，
**提前把壳摆上，等于给人三个永远是空态的 tab**——
人每次都去点一下，确认它还是空的。

### 3. 我自己走过一段弯路，也讲一下

这一段我觉得对设计判断更有参考价值。

中途我给参数卡加了一颗常驻开关，还加了「修改日志」和「当前报价表」
两个 tab。出发点都成立：想让人参数填完能回头改、想让人看得到金额和改动历史。

**但后来我把这三样都撤了。**

- 那颗开关——**"回头改"这条路本来就有**：右栏台账每行的铅笔。
  多一颗按钮换来两条线形式不一致，而它解决的问题不存在。
- 「修改日志」——**改动在对话流里本来就是一条条消息**。
  再开一个 tab 抄一遍，同一件事记两处，**两处迟早对不上，
  到那时候人不知道该信哪个**。这就是原则三。
- 「当前报价表」——金额怎么算出来的，属于"命中了哪些规则"，
  应该在规则面板里看。

但**功能一样都没丢**：那张报价表现在是规则面板上的「查看费用明细」弹窗。
**看一眼就关的东西，不值得长期占一个 tab，但它还在。**

[演示：点「查看费用明细」]

### 4. 参数卡的三级递进

[演示：折叠 → 展开 → 全屏]

最后讲一个我反复推敲过的细节。这张卡有三级：**折叠、展开、全屏**，
一级一次点击。

原来只有两级——一直铺开着，点卡片直接跳全屏。
**中间那一级被跳过了，而中间那级（就地填眼前这一组）恰恰是最常用的。**

**默认折叠**，因为这张卡不是人要求出现的——是数字同事说"还缺 3 项"时
自己冒出来的。默认铺开等于每轮对话都顶掉半屏聊天记录，
而人这时候多半只想看它说缺什么——**缺几项写在卡头上，
折叠态已经把话说完了。**

**但点铅笔出现的那张是展开的。** 人已经说明了意图，
再要他点一下才看得见，等于问他"你真的要改吗"。

**同一个组件，两种默认值，判据是"谁要求它出现的"。**
系统主动弹的收着，人主动叫的展开。

## 四、这些判断沉淀成了设计系统（2 分钟）

[打开设计系统站点]

### 1. 它不是一份样式表

上面讲的每一条判断，如果只写在这一条业务线的代码里，
**下一条业务线还会重新犯一遍**。所以我把它们写成了规则。

站点现在七节约定：**交互状态、刻度、Hover、动效、折叠展开、图标、
键盘与浮层**，加上组件和令牌。

我写的时候尽量写"**为什么**"而不是"**是什么**"。
比如折叠那节，不是写"箭头转 180 度"，而是写清楚为什么不用"朝右→朝下"
那一套——**同一个图标两种朝向，人扫视时得先辨认方向才知道状态。**

### 2. 它解决的是一个已经发生的问题

这套原型现在有二十多个全局样式表在同一个层叠里。
后果是同一个视觉维度上跑出很多种取值——**圆角一度有 56 种，
字号现在还有 36 种，而按刻度应该是 6 种。**

没有人是故意的，都是"这里差一点、我调一下"攒出来的。
设计系统就是把"到底该有几种"定下来。

### 3. 一个我特意做的调整

站点原来到处在报数——多少处没按规范写、多少个重复定义。
数字都是真的，**但我把它们全部搬走了**，搬进一份单独的清单。

理由是：**规范的说服力应该来自它自己讲得通，不是来自数别人的错。**
一个页面上挂满"某处做错了"，读的人第一反应是防御，
而不是"这条规则有道理"。

那份清单还在，每条后面写了"怎么算还清"——**它是待办，不是展品。**

## 五、一个关于产品形态的看法（1 分半）

最后说一点我自己的观察，跟前几天讨论的产品形态有关。

我们现在定下来的形态是：**中间一条对话流，右边一个可以生长的面板**——
tab 能加、能拖、能两两并列分栏。

我想说的是：**这个形态不是从"界面应该长什么样"推出来的，
是从业务里长出来的。**

举一个具体的：DMPK 报价被退回的时候，人要做的事是
**一边读退回批注、一边改参数**。这两件事必须同时在眼前——
来回切标签等于让他用脑子记。**"两两并列"这个能力就是这么来的。**

[演示：点 tab 上的并列按钮]

同样，"tab 可以生长"也不是为了灵活而灵活：
肿瘤报价现在只需要三个面板，DMPK 走通送审之后需要七个。
**面板数量是业务阶段的函数**，所以它得能长。

我的看法是：**形态的自由度应该是从具体用例里推出来的，
而不是先给一个万能的框，再指望业务自己往里填。**
后者做出来的是一个壳——每一格都能放东西，但没有一格知道该放什么。

所以如果后续要继续探索产品形态，我觉得我能补的正是这一半：
**把具体业务线走通到细节，用它去验证或者推翻那个形态。**
框架和用例，缺哪一半都立不住。

## 收尾（30 秒）

总结一下：

- 工程实现和设计语言的差别**不在审美，在假设**——
  表单是主界面还是一次回合、没填算不算填错、状态该显示几次。
- 一致性**不是长得一样**，是同一套判断在不同内容上给出各自正确的答案。
- 这些判断我沉淀成了设计系统，**下一条业务线不用重新犯一遍。**

还挡着两件要请示的：**词表要业务确认**（品系细胞系的联动、接种方式、
周期档位、"类型"那三个取值是我按常识补的），
以及 **beta3 那一版的比对**——有登录墙，想约工程师一起过一遍。

谢谢老师。

## 附：可能被问到的问题

**Q：为什么不直接复制 DMPK 改文案？**
最开始我就是这么打算的，后来放弃了。DMPK 的外壳样式在代码里出现一百多处，
散在四个文件里，其中还有两行写死的适配白名单——复制一份改名字会漏掉它们，
**窄屏会静默塌掉、不报错**。改成两条线共用同一套组件，
新业务线什么都不做就跟 DMPK 长一个样。

**Q：这么改，工程师那边要重做吗？**
功能逻辑不动。改的是这些功能**用什么形式呈现**、
以及**摆在哪一层**。他做的功能点一个没删——
"当前报价表"从常驻 tab 变成了按需弹窗，还在。

**Q：为什么删掉「修改日志」？**
不是删功能，是这件事对话流里已经记了。同一件事记两处，两处迟早对不上。
如果业务上确实需要一份可导出的改动清单，那是另一个需求，
应该按需求去做，而不是在右栏放一个抄写本。

**Q：设计系统会不会做完就没人用？**
这是我最担心的。所以它不是一份文档——**取值全部是从原型实际渲染结果里
量出来的**，而且有一套检查能验证两边还对不对得上。
规范和实现一旦分家，规范就死了。

**Q：肿瘤报价什么时候能上？**
形式已经完整。挡着的是词表确认和 beta3 比对，都不是设计量，
是要业务和工程师给答案。
