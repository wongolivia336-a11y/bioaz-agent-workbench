# 工程债清单（内部，不进设计系统站点）

> 这些是抽规范时量出来的事实，**都属于原型仓库的存量**，不是设计系统的内容。
>
> 设计系统站点是对外展示的东西，上面只说「规范是什么」，不说「谁没做到」。
> 一份规范的说服力来自它自己讲得通，不来自它数别人的错。
>
> 所以这些数字从站点上撤下来，落在这里——**是待办清单，不是罪状**。
> 每一条后面都写了「怎么算还清」，不能算清的就不该记在这儿。

数据来源：`npm run audit:ui`（原型仓库）、`scripts/token-diff.mjs`、
以及抽组件时逐个文件数出来的。日期见各条。

## 一、刻度上的欠账（最大的一块）

截至 2026-09-04（`npm run audit:ui`）：

| 维度 | 应有 | 实际跑出 | 备注 |
|---|---|---|---|
| 圆角 | 4 档 | **36 种** | 已从 56 收到 36，令牌覆盖率 83% |
| 字号 | 6 级 | **36 种** | **一直没动，三块里最大的一块** |
| 过渡时长 | 4 档 | **11 种** | 已收过一轮：119 处字面量 → 15 处，剩下的是刻意的 |
| 十六进制色 | 约 40 | **219 种** | 裸值出现次数已从 1180 → 765，覆盖率 70% |
| 关键帧名字 | 3 | **45 个** | 其中三十多个都是「东西出现了」 |
| 「出现」的位移距离 | 1 | **11 种** | −6 / −4 / −2 / −1 / 3 / 4 / 5 / 6 / 7 / 8 / 10px |

**怎么算还清**：每个维度的「实际跑出」收敛到令牌档位数 + 少数刻意的例外，
且 `audit:ui` 的基线不再倒退。

### 已经查明的具体项

- **`artifactIn` 在 `globals.css` 里定义了两次**，一份 10px 一份 7px。
  同名关键帧后定义的整个覆盖前一个——按 10px 写的规则一直在跑 7px，
  那份 10px 的定义从来没生效过。**人眼看不出来（两个都「有动」），只有数数能翻出来。**
  已删掉死的那份。
- **三个逐字节相同的转圈**：`bioazUiSpin` / `hubSpin` / `inspectorSpin`，住在三个文件里。
- **同一个动作两个名字**：`messageSendIn` ≡ `workspaceAssistantIn`，
  `quoteBubbleIn` ≡ `qaAnnotationIn`，`nodeIn` / `nodeGrowIn` 是同一个词配了两个距离。
- **三个未定义的圆角令牌**（`--bioaz-radius-pill` ×2、`--bioaz-radius-modal`）
  静默渲染成直角。已修。
- ~~**缺一个「深色底上的文字」令牌**~~ —— 2026-09-08 补上了
  `--bioaz-text-inverse`，66 处 `color: #fff` 已收（`token-diff` 1706 条 0 变化）。
  顺带发现 `color-snap` 的令牌表是 `hex → 名字` 一对一的，
  而 `#ffffff` 有**两个都对的令牌**（surface / text-inverse），
  后声明的会顶掉前一个——**结果取决于 tokens.css 里的先后顺序**。
  改成按角色查候选列表。
- **还剩 27 处角色对不上**，其中 18 处是 `border-color` 用了动作色
  （`#17191e` / `#050608`）——那是实心主按钮的边跟填充同色，本身是对的，
  但没有对应令牌。要么补一个「与填充同色的描边」，要么这 18 处留着。
  跑 `node scripts/color-snap.mjs` 会打印这张清单，数量大的那行就是下一个该补的。

## 二、同一件事有多份实现

| 东西 | 份数 | 情况 |
|---|---|---|
| 三栏网格 `280px minmax(0,1fr) 400px` | **3** | globals / iteration / review 各写一遍，收起态也是。谁生效取决于 `layout.tsx` 的 import 顺序 |
| 「它跑了一串步骤」 | **3** | `ActivityChain`（通用）/ `DmpkActivityChain`（报价）/ `ThinkingCard`（肿瘤报告），三套 DOM 三种宽度 |
| 「要人当场定一件事」的卡 | **9 个类名** | `warningDecision`、`dispatchConfirmCard`、`changeConfirmCard`、`dmpkEditProposalCard`、`dmpkReworkNotice`、`dmpkHandoffCard`、`parameterTaskCard`、`qaApprovalCard`、`reviewDecision`，共 **76 条规则**散在三个文件 |
| composer | **24 种类名 / 169 条规则 / 11 个文件** | 17 个 tsx 碰过它；2 处用现成组件，6 处自己搭了一遍 |
| Menu 的样式 | **4 个文件** | design-system 7 条、review 10 条、hub 1 条、qa-review 1 条。合并之后才能收进库 |

**怎么算还清**：每一行收敛到一份实现，且原来那几份的类名从代码里消失
（`audit:ui` 的「疑似死类名」不涨）。

### 由多份实现直接引发的用户可见问题

- **两种「发得出去」的定义**。dock 那份写的是「有字 **或** 有 chips」，
  药丸那份写的是 `!text.trim()`——画布态下选完三项参数，发送键还是灰的。
  用户已经把要说的都选完了，系统还在等他打字。
- **17 处监听 Enter 发送，没有一处检查 `isComposing`。**
  中文选词按回车会先派发一次 keydown，于是选一次词就把半截话发出去。
  **这是个中文产品，这条不是边角情况。**
- **`responsive.css` 第 51 / 68 行是写死的模块白名单**
  （`:is(.dmpk-quotationModuleShell, .tumor-reportModuleShell)`）。
  新模块不在里面，**窄屏静默塌掉，不报错**。

## 三、规范存在但没有执行层

原型那份设计规范本身写得对，末尾却写着「不阻断 typecheck、build 或 CI」。
结果：**53 处裸按钮、5 个手写弹窗**照样长了出来。

> **散文会被跳过，数字不会。**
> 这不是文档写得不好，是文档这种形式本身没有强制力。

**怎么算还清**：`audit:ui` 进 CI，基线倒退即失败。

同一个教训在设计系统这边也犯过一次：README 一直写着「组件从产品原样搬过来，
两边任何差异都是 bug」，但**没有任何东西在校验这句话**。于是对话流那一族被
照着概念重写了——圆点从 10px 白心带描边变成 7px 实心、「进行中」从一枚 chip
变成纯文字、折叠态少了 logo 灰度化、气泡丢了尾巴和渐变，还多出一个产品里
根本没有的 chevron。**看着像，没有一处相同。**

现在靠 `src/origin.json` + `npm run parity` 挡住。

## 四、两套并存、必须选一套的

- **主按钮颜色**。`.primaryButton` 实测 `#2900ff` 品牌蓝，
  `.bioazUiButton--primary` 是 `#17191e` 黑；令牌注释写着「附录 A.2 规定主按钮为黑，
  不要改回品牌蓝」。**两种都在渲染**，所以「以实际渲染为准」在这里给不出唯一答案。
  设计系统按规范取黑，模块那边的蓝算存量。
- **`:root` 有四套并存的变量**（见 memory 里的「原型层叠陷阱」）。
  抽规范只能用 `getComputedStyle` 量，读 CSS 文件必错。

## 五、按标签名写的样式（新元素会被误伤）

- `.warningDecisionList span { color: var(--amber) }`（globals.css:2588）
- `.parameterTaskCard .decisionCopy span { font-size: 12px }`（review.css:6001）

在参数行里新加一个裸 `<span>` 会被染成琥珀色粗体，而且 review.css 在
iteration.css 之后加载、特异性还更高，**覆不回来**。
新元素一律用带类名的 `<em>` / `<b>` / `<div>`。

## 怎么用这份文件

1. **不要把这里的任何一条搬到设计系统站点上。** 那个站点是对外展示的，
   它该讲的是「规范是什么、为什么这么定」，不是「谁没做到」。
2. 需要排期时按第一、二节的表拆任务——每一行都有明确的「算还清」判据。
3. 数字过期就重跑 `npm run audit:ui`，别手改。手写的数字过两周就是错的。
