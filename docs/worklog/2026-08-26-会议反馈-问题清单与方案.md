## 三个待定项已拍板（2026-08-26）

1. **编号完全消失**。前台一个字都不露，`TK-xxxx` 只留在代码模型里。
   概念模型保留——"静默在后台"指的就是这个。
2. **「已通过」算终态。** 不要复杂化：通过之后 `assignee` 换回撰写人，
   状态「已通过」，他在站内信能收到、能预览、能下载。**不计徽标、不进待办**——
   他要做的后续操作发生在这个系统之外。
3. **不建多个仓库。** 镜头由 URL 参数驱动（`?view=dmpk` / `?view=qa` / 默认总览），
   一份代码、一次部署、三个可直接分享的链接。若之后要独立域名，
   按 `docs/REPOSITORY_STRATEGY.md` 的既定策略：同一仓库连多个 Vercel project，
   用环境变量决定默认镜头，**不 fork 代码**。

   拒绝多仓库的理由是算术不是洁癖：这个项目一天改几十次，三份代码意味着
   每个 bug 修三遍，一天就分叉，一周后是三个长得不一样的原型——
   演示时老师看到三个不同的产品，比看到一个还糟。

## P1 · 交接人选择器（图一）

**老师要**：点输入框弹下拉，全公司姓名 + 搜索框。

**现状**：`modules/dmpk-quotation/views.tsx:495` 是一个裸 `<input placeholder="姓名，例如 王林彬">`。
自由文本——打错字就交接给一个不存在的人，而且没有任何反馈。

**做法**：新建 `components/ui/PersonPicker.tsx`，沉淀成通用组件。
理由：交接有**两个入口**（会话里的 `DmpkHandoffCard`、工单页的 `TicketHandoffDialog`），
现在两处各写各的输入框。不沉淀的话这次改完，下次又多一处。

UI/UX 规范（按 `docs/design-system.md` 和现有 `Menu` 组件的约定）：

- 收起态显示为一个 **chip**（头像圈 + 姓名 + 角色），不是纯文本——
  它是一个**对象**不是一段字，长得像对象才不会有人去手打
- 展开后：顶部搜索框自动聚焦，下方按**角色分组**（撰写人 / 审批人 / 负责人）
- 搜索匹配**姓名 + 邮箱**（中文姓名不做拼音，这一版不值得）
- 每行显示 姓名 · 角色 · 邮箱——你要交接给一个不熟的人时，光有姓名不够
- 键盘：↑↓ 移动、Enter 选定、Esc 收起，复用 `useDismissableLayer` 做点外部关闭
- 无结果时给一句「没有匹配的同事」，不留空白
- 已选中的那条打勾

**同时要做**：把 `inboxAccounts` 从 3 人扩到一份像样的通讯录（8–10 人，
覆盖 DMPK、QA、药效、商务几条线），并且**必须包含赵敏**。

## P2 · 交接后卡片收起（图一）

**老师要**：点完交接，卡片自动收起，化成一段用户输入发到会话里，就结束。

**现状**：`views.tsx:172` —— `stage === "generated"` 时交接卡常驻。交接完它还在那儿。

**做法**：交接成功后
1. 卡片卸载
2. 会话追加一条**用户消息**：`交接给 王林彬（审批人）：管理费按 30% 口径，请复核`
3. 追加一条数字同事回执：`已交接。这件事现在在王林彬那儿，产物已随行。`

**我认同这个改法，理由**：交接卡是一个**临时的输入界面**，它的产物应该沉淀成
对话里的一条记录。留一张已提交的表单在原地，等于让人反复看见一个不能再操作的
控件——而会话的价值恰恰是"从上往下读就知道发生过什么"。

## P3 · 去掉「工单」字眼（图二、图三）

**老师要**：工单相关字眼都去掉，静默地在后台做，给用户看得简洁。

**现状**：用户可见的只有 5 处（其余全是代码注释——**注释保留**，
内部模型仍然是工单，这正是"静默在后台"的意思）：

| 位置 | 现在 | 改成 |
|---|---|---|
| `TicketsPage.tsx:221` | `搜索标题、发件人或工单号` | `搜索主题、发件人或项目` |
| `TicketsPage.tsx:345` | `aria-label="工单进度"` | `处理进度` |
| `QuoteReviewCanvas.tsx:61` | `工单状态` | `状态` |
| `QuoteReviewCanvas.tsx:84` | `随工单留档` | `随这条消息留档` |
| `views.tsx:485` | `交接后这张工单会出现在…` | `交接后这件事会出现在…` |

**面包屑 `TK-2047` → 主题**：
主题很长（「请审批：硝酸异哈哈梨酯检测报告（第一版）」），面包屑会被撑爆。
做法：`max-width` + ellipsis，`title` 给全文。

> ⚠ **要你定的第一件事：编号完全消失，还是留在详情页？**
>
> 我的建议是**面包屑改主题，但编号留在详情页那行元信息里**
> （现在是 `TK-2046 · 报价复核 · 全程人工 · 复核人 王林彬`，本来就没写"工单"两个字）。

> ——那是高频位置，不该被一串编号占着；但完全删掉，追溯就只能靠描述。
>
> 如果你觉得连详情页也不要，我就删，这不影响其他任何事。

## P4 · 去掉「归档」，通过后交回撰写人（图四）

**老师要**：归档字眼去掉。通过之后返回给撰写人，他们站内信收到「已通过」，
再去做后续操作。因为数据中枢还没完全做好。

**现状**（`WorkbenchShell.tsx` `archiveTicket`）：状态落成 `done`，
**`assignee` 不变**。所以通过之后单子停在审批人名下，撰写人那边什么都收不到——
弹窗上写着"交接给 数据中枢"，但代码里并没有真的交给谁。**这本来就是个空头承诺。**

**做法**：
- `archiveTicket` → 改名 `approveTicket`：`assignee` 换回 `ticket.from`，状态 `已通过`
- 按钮 `通过并归档` → `通过`
- 弹窗标题 `通过并归档` → `通过`，`确认归档` → `确认通过 · 交回 赵敏`
- 弹窗事实行：`交接给 数据中枢` → `交接给 赵敏（DMPK 报价同事）`
- 状态标签 `已完成` → `已通过`

> ⚠ **要你定的第二件事：「已通过」还算不算终态？**
>
> 这条必须想清楚，否则会出一个隐蔽的 bug。
>
> 现在 `done` 是终态：不计侧栏徽标、不进「待我处理」。
> 但按老师的说法，撰写人收到「已通过」之后**还要做后续操作**——
> 那对他来说这就是一件待办，不计徽标是错的。
>
> 三个选择：
>
> **(a) 保持终态**：撰写人能在收件箱看到，但不亮徽标。
> 　　代价：他真正要做的那一步没有任何提醒，很可能被漏掉。
>
> **(b) 不再是终态，计入徽标**（我建议这个）。
> 　　代价：流程暂时**没有终点**，所有通过的单会一直挂在撰写人待办上。
> 　　但这恰恰是**真实情况**——数据中枢没做好，落库的地方还不存在，
> 　　流程本来就还没有终点。假装有终点才是不诚实。
> 　　我会在代码注释和文档里写明这是临时状态。
>
> **(c) 给撰写人加一个「确认收妥」动作**把它落到终态。
> 　　代价：多一个此刻没有真实含义的按钮——他"收妥"之后东西去哪儿了？
> 　　数据中枢还没建好，这一步是空的。
>
> 我选 (b)：让界面如实反映"这条链还没修完"，比造一个假终点好。

## P5 · 撰写人进会话回到原 session（图五）

**老师要**：驳回给撰写人之后，他站内信收到消息，点进去可以「进入会话处理」，
带回到**当初产出这份报价单的那个会话**，同一个 session。

**现状**：DMPK 工单对任何可处置的人都显示「开始审核」→ 就地进批注台。
撰写人点进去会看到一个**批注台**——可他不是来批注的，他是来改的。

**好消息**：回原会话的能力已经有了。`startTaskFromTicket` 会按 `ticket.taskId`
接回原任务，而且有 module 匹配守卫（防止 QA 工单掉进药效报告工作台，这个 bug 犯过）。
缺的只是**按角色分岔**。

**做法**：`TicketDetailView` 里判断这个人在这张单里的位置：

```
currentUser === ticket.from   → 他是撰写人 → 「进入会话处理」→ 回原 session
currentUser === ticket.assignee 且 ≠ from → 他是被交接的那一棒 → 「开始审核」→ 就地审
```

**这个判据自洽**：驳回时 `assignee` 换回 `ticket.from`，所以撰写人同时是 from
和 assignee，走第一条；审批人是 assignee 但不是 from，走第二条。
不用引入"角色"这个新概念——**一个人在这张单里是什么身份，单子自己说得清。**

## P6 · QA 和 DMPK 拆开演示（最需要讨论的一条）

**老师要**：QA 和 DMPK 分开展示，先演示好 DMPK 的撰写人↔审批人。
建议加一个演示入口：总览 / QA 审核 / DMPK 报价。账号切换对应不同职责的流转。

**现状**：
- 站内信**已经有**「类型」筛选（全部类型 / QA 审核 / DMPK 报价 / 数字同事知会 / 系统通知）
- 但它只管收件箱，不管侧栏项目树，也不跟着账号走
- 账号切换器只有 3 人，**没有赵敏**，DMPK 那条线切不过去

**做法**：一个「演示视角」控制，三档，同时收敛三样东西：

| 视角 | 侧栏任务 | 收件箱类型 | 可切换账号 |
|---|---|---|---|
| 总览 | 全部 | 全部 | 全部 |
| QA 审核 | 只留 QA 任务 | 预设 QA 审核 | 林一一（一线实验员）↔ 王林彬（审批人） |
| DMPK 报价 | 只留 DMPK 任务 | 预设 DMPK 报价 | **赵敏（DMPK 报价同事）** ↔ 王林彬（审批人） |

**这是演示脚手架，不是产品功能。** 真实的 CRO 里一个人只有一个角色，
不会切换——账号切换器本身就已经是演示装置（`ticketData.ts` 的注释里写明了）。
所以在它旁边再加一层镜头是**一致的**，不是新增了一个产品概念。

我会在组件里写明「上线前删除」，并记进 `docs/design-system.md` 的待办。

> ⚠ **要你定的第三件事：演示入口放首屏，还是放顶栏？**
>
> **首屏拦截页**：一打开就选一条线，最符合"演示入口"这个说法，
> 老师体验最顺。代价是**每次 dev 刷新都要多点一次**——这个项目一天要刷几百次。
>
> **顶栏切换器**（我建议这个）：默认「总览」，随时切，不挡路。
> 代价是老师第一眼不会注意到它，需要你在演示时主动指一下。
>
> 折中方案：**放顶栏，但用 localStorage 记住上次选择**。
> 演示前你切到「DMPK 报价」，之后每次打开都停在那条线上，
> 直到你手动切回总览。这样既不挡日常开发，演示时又不用每次重选。
>
> 我倾向折中方案。

## 我不打算做的，以及为什么

- **不删「工单」这个内部概念。** 老师说的是"给用户展示得简洁"，
  不是"把模型拆了"。工单是这套流转能成立的原因（一份产物一张单、来回几轮
  都记在一条链上、状态一翻交接就存在）。把它从**措辞**里拿掉是对的，
  从**模型**里拿掉会让"这份报告审了几轮、现在在谁手上"重新变成需要人去拼的事。

- **不给「已通过」造一个假的归档终点。** 见 P4 的选项 (c)。

- **不做 QA 那条线的深度改造。** 老师说先演示好 DMPK。QA 这次只做到
  "能被镜头筛出来、不干扰 DMPK 演示"，不动它内部的流程。
