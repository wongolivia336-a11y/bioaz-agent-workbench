## 一、今天做了什么

### 1. 右侧面板加了「全屏」形态，对话收成悬浮胶囊

**要解决的问题。** 右侧面板宽度固定 400px，但里面装的东西宽窄差异很大——参数收集是一列表单，报价规则和计算依据是宽表。宽表挤在 400px 里要横向滚动，读一行得来回拖。做 QA 审核时这个问题会更严重，因为审核的对象是整份交付包。

**做法。** 面板 tab 栏右端加一组视图操作 `[ + ] │ [ ⤢ ]`，两组语义之间一条淡竖线。点 `⤢` 面板铺满工作区，对话列淡出，底部中央换成一颗悬浮胶囊。

三个决定值得记一下：

- **全屏只吃对话列，topbar 和左侧任务栏保留。** 「全屏」是相对工作区而不是相对浏览器——审核到一半丢掉面包屑和任务切换，用户会慌。
- **收起按钮没有跟着挪进 tab 栏。** 参考的那个产品能把两个图标并排放，是因为它面板收起后那条栏还在；我们的面板收起后自身不渲染，开关跟着消失就没有回来的路。所以 topbar 那个 `PanelRight` 留在原地，tab 栏只加 `⤢`。
- **`⤢` 不是对所有面板都亮。** 参数表、缺失项这类单列内容放大只是把留白拉长。给面板定义加了 `expandable` 标记，目前只有报价规则、计算依据、报价结果、审核记录四个是 true，其余置灰但保留占位——移除的话加号会跟着 tab 切换左右横跳。

**悬浮胶囊的三态。** 静默（只有输入框）→ 播报（agent 新消息浮在胶囊上方，3.5 秒后淡出，胶囊上留一颗未读点）→ 展开（560×420 浮层对话，从胶囊向上生长）。

为什么是底部中央的胶囊，不是角落小卡或客服气泡：角落小卡会一直挡住画布；FAB 断了 agent 主动播报的路，说了话你不点开不知道。胶囊赢在它和 composer 是**同一套形状语言**，切换时视觉上是「同一个东西收小了」，而不是「对话消失了、冒出个新玩意」。

**一个没做到的取舍要如实说。** 原本想让面板做宽度形变（从 400px 长到满宽），实际放弃了。面板里有表格，逐帧改宽度会让列宽反复重算，抖得比不动还难看。最后是交叉淡入 + 短位移，240ms 内完成。连续感交给 composer → 胶囊这一层去承担。

### 2. 图标系统的技术债

先做了一次清点，账单比预想的具体：全仓 401 处图标用了 **14 种尺寸**（11 到 28）。更能说明问题的是同一个图标的分裂——`X` 渲染在 7 种尺寸上，`Check` 5 种，`Plus` 4 种。14 和 15 差 1px 肉眼分不出，但意味着没人知道该写哪个。

清掉四笔：

| 债 | 处理 |
|---|---|
| `types/lucide-react.d.ts` 89 行手写声明盖住了 lucide 自带的完整类型，每加一个图标都要手工补一行 | 整个文件删除，`tsc` 直接通过，零代码改动 |
| 同一字形两个名字（`HelpCircle`/`CircleHelp`、`AlertTriangle`/`TriangleAlert`）都在用 | 统一到 lucide 规范名 |
| 描边有 3 个来源、5 个值：376 处吃默认 2，25 处手写 1.6~2.4，CSS 里另有 8 条覆盖 | 一条 `.lucide { stroke-width: var(--icon-stroke, 1.75) }` 收口；删掉 27 处已失效的 `strokeWidth` 属性；CSS 改成覆写变量 |
| 尺寸没有标度，且 JSX 与 CSS 互相打架（首页快捷卡 JSX 写 16、CSS 强制 18） | shell 层 10 档收成 12/14/16/20/24 五档；删掉 CSS 的 width 覆盖，尺寸只看属性 |

描边那笔有个关键点：lucide 给每个图标都带 `class="lucide"`，所以一条 CSS 规则精确命中图标、碰不到 BioAZ logo 那几个手写 SVG。而 CSS 的 `stroke-width` 会盖过 lucide 写在元素上的 presentation attribute——这也意味着 JSX 里的 `strokeWidth` 从此不生效，留着就是骗人，所以一并删了。需要加重的地方（11px 叉号、实心按钮里的箭头）改成在自己的 CSS 规则里覆写 `--icon-stroke: 2.3`。

**实测结果。** 首页 37 个图标，尺寸只剩 14/16，描边只剩 1.75 和 1.5（后者是刻意保留的两处加轻）。会话页 45 个：12/14/16，另有两个 15/18 落在 `modules/dmpk-quotation/` 里——那是范围之外，符合预期。控制台无报错。

标度和机制写进了 `docs/design-system.md`，否则下一轮又会散。

### 3. 一个自我纠正

一开始想把 `Edit3` 合并到 `SquarePen`，查了包才发现 `Edit3` 等于 `PenLine`，和 `SquarePen` 是**两个不同字形**。所以 DMPK 用 `Edit3`、肿瘤报告用 `SquarePen` 不是别名重复，是同一个「编辑」动作画了两支不同的笔。这是设计一致性问题，不是能顺手合并的技术问题，留给后面定。

## 二、纵向比对：这半年面板是怎么走过来的

把今天的改动放回时间线上看，会发现它不是一个孤立的功能，而是一条线的下一步。

| 代次 | 形态 | 「面板什么时候出现」由谁决定 | 「面板占多大」由谁决定 |
|---|---|---|---|
| 一 | 三按钮互斥入口 | 系统（点哪个开哪个，且互斥） | 固定 |
| 二 | `WorkbenchInspector`：hover 唤出 + pin 固定 | 系统唤出，用户可 pin | 固定 |
| 三 | `WorkbenchPanelBody`：tab 栏 + 加号，常驻右列 | 用户（自己决定装哪些 tab） | 固定 400px |
| 四（今天） | dock ⇄ focus 两态 + 悬浮胶囊 | 用户 | **用户** |

**这条线的主轴是：面板的存在感持续下降，可控性持续上升。**

- 第一代和第二代，面板是系统「弹给你看」的东西，用户是被动的。第二代的 pin 是用户第一次拿到控制权，但只是「别再自己关掉」这一点点。
- 第三代把「装哪些面板」交给用户，这是决定权的一次真正转移——代码注释里那句「系统永远不会自己把它们加回来」就是这个意思。同时保留了「阶段推进时打一个小圆点，不抢视图」，即系统只提示、不夺权。
- 第四代把最后一个维度——**空间**——也交出去了。

这个视角能预测下一步该做什么：**宽度拖拽**。今天做的是离散两档（400px / 满宽），中间那段连续控制还没有。而 `--panel-width` 已经是变量了，改造成本不高。

另外一个可以拿出来讲的对比，是**治理方式本身的转变**。图标这件事上，之前的做法是「就地拍一个值」——25 处手写 strokeWidth、8 条 CSS 覆盖，每一处单看都合理，合起来就是没人知道规则是什么。今天的做法是「定一个机制 + 写进文档 + 留逃生口」。这个转变比具体改了几个像素更值得说。

**顺带查出两处旧代的残留**（今天没动，见明日计划）：

- `WorkbenchInspector` 组件本体 189 行（第二代的 hover/pin 模型），当前 **0 处引用**——只有它文件里的类型定义和 `resolveInspectorPanels` 还在用。
- `components/workbench-inspector/dmpkInspectorPanels.tsx` 是个纯转发文件，也是 0 处引用。

这两处存在本身就是「面板在收敛」的物证，适合放进汇报。

## 三、明天要和老师讨论的两个问题

### 问题一：这种形式的画布，能不能涵盖 QA 审核？

**我的判断：覆盖一半。全屏那半是对的，tab 那半是错的。**

QA 审核的核心循环是——看一条清单项 → 在文档里找到证据 → 判定通过与否 → 记录理由。这个循环里，**清单和文档必须同时可见**，它们不是「二选一」的关系。而 tab 模型的前提恰恰是「这些面板是互相替代的，你一次只看一个」。

所以：

- ✅ **全屏是对的。** 交付包是宽内容，400px 装不下，这正是今天做 `⤢` 的动机。
- ❌ **tab 不适用。** QA 需要的是画布**内部**再分栏（清单约 320px 固定在左，文档占剩余），不是在清单和文档之间来回切 tab。
- ✅ **悬浮胶囊对 QA 其实比对报价更合适。** 报价的对话是主流程（参数靠对话补齐）；QA 的主流程走清单上的判定按钮，对话只承担「问一句」——「这条为什么不通过」「上一版这里是什么」。把对话降级成辅助通道，正是胶囊在做的事。

**但有一个真问题要先答：QA 的结论必须留痕。** 如果审核员把判定理由打进悬浮胶囊，那这句话是一条聊天消息，还是一条审核记录？如果只是聊天，「审核记录」面板里就没有它，追溯链断了。

两条出路，我倾向第二条：

1. 胶囊里的消息识别为判定理由时，同步写入审核记录 —— 靠猜，不可靠。
2. **判定完全不走胶囊**，走清单项上的结构化控件（通过/不通过 + 理由输入），胶囊只用于问答。留痕的是控件，不是对话。

第二条的代价是「所有判定都要点控件」，但审核这件事本来就需要结构化，这个代价是应该付的。

**需要老师定的：** QA 审核的分栏比例和清单的粒度（一条一条判，还是按章节批量判）。这个定了画布的布局才能定。

**现状提醒：** `modules/qa-review` 目前是 placeholder，`availability: "placeholder"`，只有一句 handoff note「后续接入审核清单与证据追溯」。所以上面全是设计推演，第一版只能在 DMPK 报价的画布上验证机制，QA 接进来时复用。

### 问题二：报价规则更改要不要展开画布？

**现状是断裂的。** 用户在对话里说「以后 PK 样品少于 X 个按 Y 个收费」，系统识别成全局规则草稿，然后——

```
window.location.href = `/?view=quotation-management&business=dmpk&tab=rules&draft=...`
```

整页跳走，把草稿当 URL 参数带过去。用户离开了他正在做的那单报价，到另一个页面重新找到那条规则。

**「后台挪到前台 + 胶囊做输入」这个想法我认为成立，但不应该整个搬。**

支持的理由：
- 规则表是宽表，正是 `expandable` 该覆盖的内容类型——今天已经给规则面板标了 `expandable: true`，画布是现成的。
- 自然语言拟规则的能力（`DmpkRuleAssistant`）已经存在，只是长在管理后台里。挪到前台不是新建能力，是搬运。
- 最重要的：**用户不用为了表达一句话就离开现场。**

但有一个不能丢的东西——**跳转这个动作本身在传递信号：你正在离开这一单业务，进入配置领域。** 改全局规则影响的是后续所有报价，不是当前这单。做成原地展开，这个信号就没了，风险是用户随手改了全局规则还以为只改了这一单。

代码里其实已经把概念分清楚了：`editProposal` 有 `current-price`（仅本次）和 `global-rule`（影响后续，发布前需验证）两种，文案也写明了。所以问题不是概念不清，**是交互上怎么把这条边界画出来。**

**我的建议：搬「拟草稿」，不搬「发布」。**

| | 放在哪 | 负责什么 |
|---|---|---|
| 表达意图 + 看见影响 | **前台**：规则面板全屏 + 胶囊自然语言输入 + 实时 diff 预览 | 用户留在现场，说完就能看到这条规则改了哪几行、影响哪些历史报价 |
| 发布 + 版本 + 生效范围 | **后台**：管理页 | 边界仍在，且发布这一步值得一次显式的跳转 |

这样边界还在（发布依然要出门），但用户不用为了表达一句话就出门。

**需要老师定的：** 前台改完之后，是直接进草稿队列等后台发布，还是需要当场走一次审批？这关系到「谁有权改全局规则」，是权限问题不是交互问题。
