## 二、这套东西现在长什么样

```
收件箱图标（徽标 = 待我处理的工单数）
└── 站内信            一个列表。消息形态：发件人 · 主题 · 项目/附件 · 状态 · 时间
    │                 筛选：搜索 | 状态▾ | 类型▾ | 项目▾
    ├── 纯通知  →  通知正文（无状态、无流转、看过就翻篇）
    └── 工单    →  工单详情（状态条 + 随单产物 + 流转记录）
                  ├── QA 审核    →「进入会话处理」跳任务会话（要跟数字同事一起看）
                  └── DMPK 报价  →「开始审核」就地进批注画布（全程人工，不跳走）
                                  └── 计算表 ⇄ 报价书 双形态，共用锚点
                                      选中文字 → 就地气泡卡 → 右栏记录
                                      驳回（打回提交人）/ 通过并归档（进数据中枢）
```

### 几条不要推翻的设计决定（都有具体理由）

| 决定 | 为什么 |
|---|---|
| 工单是独立对象，站内信只**指向**它 | 一张单来回几轮会产生多条消息；工单若挂在消息下，同一件事就有 N 个门没有地址，手动交接的单也无处安身 |
| 「待我处理」判据是 `assignee`，不是状态名 | 「已驳回」是审批人视角起的名字，可球这时在撰写人手上——用状态名筛会让他看到一片空白，而他确实欠着一件事 |
| 机机协作不产生站内信，除非需要人 | 否则收件箱被机器人的交谈填满，而它的全部职责是「装那些想要一个人的事」 |
| 批注锚在**行**上，不是文本坐标 | 报价单本来就是结构化的；有名字的行比一段坐标好定位，下一版也更容易验证「那一条改了没有」 |
| 批注带 `suggested` 建议值 | 报价复核是算术。「应该是 6 不是 2」能被下一版直接核验，不用人肉比对 |
| DMPK 批注台不带 AI 对话 | 全程人工。拉个 chatflow 进来只会长出「这里能问 AI 吗」的期待，而它确实不能 |
| 工单类型决定打开哪个工作台 | 关联任务只说明产物从哪来。照任务的 module 走，QA 工单会掉进药效报告工作台（这个 bug 犯过一次） |

## 四、这个代码库的几个坑（吃过亏，写下来）

**PowerShell 不要用来改代码。** 单元素嵌套数组会被拍平，我因此把 `WorkbenchShell.tsx` 里每个 `o` 换成了 `n` 且不可逆，只能 git 恢复重做。含模板字符串或特殊字符的替换一律走 Edit 工具。另外 `cmd.exe /c` 起进程会让中文路径变乱码，误导排查方向。

**grid 嵌 grid 会默认拉伸。** 子项被父容器分到固定高度后，若不写 `align-content: start`，内容会平分整格高度。这个坑在消息列表和详情页宽度上各踩了一次。写新面板前先在浏览器里量，别靠推理。

**比较要同层级。** 拿内容盒比边框盒会把修好的判成没修好——`.workbenchView` 自带 51.2px 内距，这一点误导过我一次。

**portal 会逃出作用域。** `.parameterTaskCard` 和 `.dmpk-quotationModuleShell` 里装的不是外观是**决策**（布局改写、指针行为禁令、配色收敛）。portal 到 body 的东西必须把选择器写回去，用 `:is()` 扩，不要复制——复制的那份迟早跟本体分叉。

**review.css 的特异性很乱。** 光 composer 的几何就有 6 条规则在抢，我追「最后生效的那条」追过三层。在这个文件里写样式，实测计算值，别信推理。

**磁盘可能坏文件。** 今日 `node_modules` 被写坏（262 个 package.json 里 8 个是二进制乱码）。遇到 `Invalid package config` 类报错先怀疑磁盘：
```bash
node -e "JSON.parse(require('fs').readFileSync('<file>','utf8'))"
```
另：**PowerShell 的 `ConvertFrom-Json` 会误报 npm lockfile 损坏**（根条目用空字符串做 key 是合法 JSON），验 JSON 一律用 node。
