# QA 审核动线重构交接

更新时间：2026-08-17

开发分支 `codex/dmpk-composer-params`。本文件记录 QA 审核这一轮的**已确认决策**，供下一位接手时直接执行，不必重新讨论。

## 交接结论

QA 审核不再是「工作台 + 三个页面」，改为**一个贯穿报告全生命周期的 Session**：

```
Inbox 是入口
Task Session 是整个审核生命周期
ChatFlow 是 QA Agent 的任务控制中心
Panel / Canvas 是同一块区域的两种尺寸
AI审核 = 发现问题 · 修改比对 = 验证是否被解决 · 审批 = 最终决策
版本由系统自动维护，不让用户手动上传第二份文件
```

**当前进度：数据模型（第 1 件）已完成，UI 尚未开始。**

## 一、不可动摇的三条

这三条是后续所有实现的前提，改动它们等于推翻本轮结论。

### 1. Session 挂在「报告」上，不挂在「审核轮次」上

同一份报告从 V1 到批准，**始终是同一个 Session**。退回不结束 Session，它进入「等待撰写人修改」状态；新版本到达是这个 Session 的一个事件。

理由：跨版本才回答得了「上一轮的问题解决了吗」，而那是审批人唯一真正关心的事。拆成多个 Session 就跨不过去了。

### 2. 收件箱是唯一的**创建**入口，但不是唯一的**进入**入口

从邮件「开始审核」创建，保证 Session 必然携带**项目 + 文件 + 撰写人 + 版本**四件套；创建之后，侧栏任务列表随时可以回去。这两件事不要混为一谈。

「开始审核」时自动完成：识别项目 → 关联报告 → 识别版本 → 建立与上一被退回版本的关系 → 启动 AI 审核。

> ⚠ **启动 AI 之前必须先确认版本归属**，否则会对着错版本跑一遍。

### 3. Panel 和 Canvas 不是两种内容，是同一块区域的两种尺寸

| | 内容 |
|---|---|
| **Panel（窄）** | 只有当前状态的列表，文档看不见 |
| **Canvas（全屏）** | 文档 ＋ 当前状态的列表，并排 |

**所有状态都能全屏，不只有文档。** 「文档」之所以不需要独立 Tab，不是因为它搬去了 Canvas，而是因为**文档是每个 Canvas 的左半边、一直都在**。它和「问题 / 变更 / 审批」不是并列关系——那三个是*结论*，文档是*被审的东西*。

全屏 = 铺满面包屑以下、sidebar 以右的整个区域；ChatFlow 收起；composer 变居中悬浮胶囊。

进入 Canvas 的两条路（都要）：面板展开键（手动）／点某条问题或变更（自动）。退出回到 Panel 时**当前 Tab 和选中项不变**。

## 二、数据模型（本轮已实现）

### 改造前的四个缺口

| 需要的能力 | 原模型 | 缺什么 |
|---|---|---|
| 上一轮问题解决了吗 | `QaFinding` 无版本字段 | 问题不知道自己是哪一版提的 |
| 这处修改对应哪条问题 | `QaDiffRow` 只有 `page/field/before/after/kind` | 没有 `issueId`，diff 与问题是两个孤岛 |
| 已修复 / 未修复 | 只有 `QaFindingState = open \| accepted \| dismissed` | 那是**QA 认不认这条问题**，不是**撰写人改没改好** |
| 和上次被退回的版本比 | `QaVersion` 无关联字段 | 表达不了「上一次被退回的版本」 |

### 两个轴必须分开

这是最容易做错的地方：

- **`disposition`（QA 处置）** — QA 认不认这条问题：`open / accepted / dismissed`
- **`repair`（修复结论）** — 撰写人改没改好：`fixed / partial / unfixed / regressed`

一条问题可以同时是「QA 已采纳」＋「撰写人未修复」，也可以是「QA 已忽略」＋「撰写人反而改了」。塞进一个字段就永远说不清。

### 状态取值的语义

`repair` 里的 `regressed`（改回去了 / 越改越糟）不是凑数——假数据里就存在：`收检日期 2025-12-12 → 2025-11-10`，把日期往前挪，很可能制造新的时间逻辑问题。

「新增问题」和「无关修改」**不是**遗留问题的修复状态，它们是本轮内容的分类：

- 遗留问题 → 每条一个 `repair` 结论
- 本轮新增问题 → 独立一批 `QaIssue`（`raisedIn` 指向当前版本）
- 无关修改 → `QaChange` 中 `issueId` 为空的那些

混进一个枚举会让 UI 说谎。

### 三重编号必须一直成对显示

同一份报告里有**三套编号**在打架：

1. 版本号（V1 / V2 / V3）
2. 文档页（PDF 的第几页）
3. 内部标注页（页面上印的「4/7」）

假数据里 `docPage: 2, innerPage: "1/7"` —— 文档第 2 页上印着「1/7」；而问题文本本身还写着「出现第 17 页/共 7 页」。

**处理规则：版本一律带 `V` 前缀和日期；页码一律成对显示（`文档第 5 页 · 标注 4/7`）；任何地方都不允许出现裸数字。**

## 三、三个 Tab 的最终形态

改名（Tab 应命名用户要找的**对象**，不是产出它的机器）：

| 原名 | 新名 | 理由 |
|---|---|---|
| AI文件审核 | **问题** | 用户找的是"有什么问题"，不是"AI 的文件审核" |
| AI文件比对 | **变更** | 「比对」暗示用户要自己提供两份东西 |
| 审批备注 | **审批** | 「备注」把决策说成了附注 |
| 文档 | **删除** | 文档是每个 Canvas 的左半边，不是并列状态 |

| Tab | Panel（窄） | Canvas（全屏） |
|---|---|---|
| **问题** | 按类别分组的清单，每条带双编号 ＋ 处置状态 | 文档 ＋ 清单，点一条跳页并高亮 |
| **变更** | 汇总计数一行 ＋ **表格**（遗留问题 / 对应修改 / 修复状态） | 文档 ＋ 表格；双栏是这里的一个开关，带同步滚动 |
| **审批** | 已处置意见清单（AI ／ 人工混排）＋ 决策区（通过 / 驳回 / 转办） | 文档 ＋ 上述全部 |

### 「问题」承载一轮的全部结论

与最初设想不同：**V2 之后，「AI 审核」和「修改比对」是同一次 AI 跑批的两个输出，不是两个动作。**

- V1 时根本没有比对，那个 Tab 会是空的
- V2 时一次跑批同时产出「本版新问题」和「遗留问题的结论」，劈到两个 Tab 会逼用户来回对

所以：**「问题」承载这一轮的全部结论**（遗留问题按 `repair` 排序 ＋ 本轮新增），**「变更」只回答"他还动了什么"**（含无关修改）。这样 V1 时「变更」自然为空且合理。

### 比对的默认形态是表格

修正早期结论（早期把表格漏了）：

- **默认 = 表格**，因为「QA问题 ↔ 修改 ↔ 修复状态」需要列才放得下
- **点一行 → Canvas 定位 ＋ 就地展示前后**
- **左右双栏 = Canvas 内的开关**，带同步滚动，只在需要通读上下文时用
- **全文标记所有修改**不作为独立模式，它是「变更」里"无关修改"那部分的形态

## 四、从旧版抢救 / 丢弃清单

旧版指 `QA审核系统 > 任务审批` 那套独立页面。

### 必须捞回来

| 元素 | 归属 | 理由 |
|---|---|---|
| **当前页双编号常驻读数**（`文档第3页(整体) / 内部2/7(内部)`） | Canvas 顶部页码控件 | 旧版做对而新版丢了的最重要一件。新版只在**每条问题**上标了页码，没告诉你**你现在翻到哪儿** |
| **差异表格视图** | 「变更」Tab 默认形态 | 骨架直接复用（`总页数 / 内部页数 / 修改类型 / 修改前 / 修改后`），加「对应问题」「修复状态」两列 |
| **同步滚动开关** | Canvas 双栏模式内 | 不是常驻控件 |
| **差异汇总计数**（新增 N / 删除 N / 修改 N） | 「变更」Tab 顶部一行 | |

### 丢弃

| 元素 | 理由 |
|---|---|
| **语义指标**（平均相似度 / 内容保持度 / 结构完整性） | 三个数全是 1.0000，对审批决策零信息量。模型在自评，不是给人看的 |
| **「进入审阅模式」按钮** | 它就是 Canvas Mode，不需要第二个入口 |
| **顶栏的「通过审批 / 驳回审批」** | 位置不对：旧版能在任何 Tab 直接通过，**可以没看问题就点通过**。现版把它放在「审批」里并在 `openFindings > 0` 时禁用，**这个门禁不要退回去** |
| **「下载比对表格」按钮** | 归 Agent 能力：「把变更导出成表」 |

「转办」保留，放「审批」Tab 里和通过 / 驳回并列。

## 五、ChatFlow 的边界

**判据（比列清单管用）：**

> 有稳定身份、你会回头指着它的 → Panel / Canvas
> 为此刻生成一次、说完就过去的 → Chat

| 进 Chat | 进 Panel / Canvas |
|---|---|
| 我正在检查什么（活动链） | 问题清单 |
| 一句话结论 ＋ 数字 | 每条问题的页码、证据、状态 |
| 「这条为什么成立」的解释 | 版本时间线 |
| 版本差异的**叙述** | 变更逐条 |
| 修改建议草稿 | 审批记录 |

补充规则：

- **AI 跑批时输出过程，跑完折叠成一行**，结构化结果去 Panel。**不要把 N 条问题贴成 N 段聊天**——那样它们就失去身份，没法被点击、排序、标状态
- **点问题 → Canvas 定位，Chat 不产生消息**。只在 composer 上挂一枚上下文 chip（`问题 #3 · 第 8 页`）。往 Chat 写「你点击了问题3」是噪音
- **选中文本 → 变成 composer 里的引用 chip**
- **「再检查一下第 8 页」→ Agent 定位并重跑该页**。这条和上一条是 Canvas 与 Chat 必须共存的理由——**Agent 能操作视图才叫陪着你干活**，否则只是个侧边栏问答
- Canvas 里 composer 挂一枚 **scope chip**（全文 / 当前页 / 选中文本 / 当前变更），点问题时自动切到该问题。用户永远知道自己在问谁

### 其他诉求一律不给 Tab

**判据：需要反复回来、并且要能指着它说话的，才配有 Tab。其余都是请求。**

查看 SOP / 询问规则 / 解释问题 / 修改建议 / 重新检查 / 导出问题 / 查看修改原因 → 全部走 Chat。
文档搜索 → Canvas 内工具。查看历史版本 → 版本 chip。
**添加人工批注 → 并进「问题」**，作为 `source: "human"` 的问题：它和 AI 提的问题是同一类对象，都要被退回、被验证、被标状态。

## 八、环境坑（会浪费下一位大量时间）

### 1. Next dev 的构建缓存会卡住 CSS

改了 CSS、硬刷了、计算样式却还是旧值——**不是层叠问题，是 dev server 没重新编译**。本轮实测：源文件已是 `display: flex`，而 `fetch` 服务端 CSS 拿到的仍是 `inline-flex`。

**排查方法**（比看 computed style 可靠）：

```js
const href = document.querySelector('link[rel=stylesheet]').href;
fetch(href).then(r => r.text()).then(t => console.log(t.slice(t.indexOf('.你的选择器'), 200)));
```

**解法**：停服务 → `Remove-Item -Recurse -Force .next` → 重启。

### 2. 浏览器面板隐藏时，rAF 与 CSS transition 不推进

页面不可见时 `requestAnimationFrame` 不回调、CSS transition 卡在 `running` 状态永不完成，于是：

- 依赖 rAF 的组件（如 `SessionMinimap`）不更新
- 读 `getComputedStyle` 拿到的是过渡的**起始帧**，不是终值
- 入场动画冻在第 0 帧，会让元素带着起始态的 `scale/translate` 被量到

**取真值的办法**：临时 `el.style.transition = 'none'` ＋ `el.getAnimations().forEach(a => a.finish())` 再测。

### 3. `npm run build` 在这台机器上必然 EISDIR

与改动无关。验证一律用 `npm run typecheck`。
